# VS Code Remote-SSH port discovery and forwarding

_Researched 2026-08-12. “Verified” below means supported by an official VS Code document, Microsoft-owned repository/issue log, or OpenSSH documentation. Source links into `microsoft/vscode` are pinned to commit [`96f2210`](https://github.com/microsoft/vscode/tree/96f2210282fa5c1528ecac70a73180c4d6292c89)._

## Executive summary

VS Code uses **two different tunnel layers**:

1. Remote-SSH starts the VS Code Server and carries VS Code’s remote-agent connection through OpenSSH. Current public Remote-SSH logs show a supervised system-SSH child such as `ssh -T -D <local-port> …`; `-D` creates a local dynamic SOCKS forward ([issue log](https://github.com/microsoft/vscode-remote-release/issues/10939), [`ssh(1)`](https://man.openbsd.org/ssh#D)). Official troubleshooting also describes two logical SSH connections—one to install/start or locate the server and another to create the tunnel to it—and recommends `ControlMaster` only as an optional macOS/Linux-client workaround ([documentation](https://code.visualstudio.com/docs/remote/troubleshooting#_connecting-to-systems-that-dynamically-assign-machines-per-connection)).
2. A temporary/user or automatic application-port forward is represented by VS Code’s public tunnel model. The public default implementation opens a Node local TCP listener and, for each accepted socket, requests a connection to the target host/port through the **existing VS Code remote-agent transport**; it is not an added `ssh -L` process ([`NodeRemoteTunnel`](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L24-L146)). A resolver extension may replace that implementation with a tunnel provider ([provider bridge](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/browser/mainThreadTunnelService.ts#L171-L211)); the Remote-SSH extension is closed-source, so its current provider decisions are not publicly auditable.

This design works on native Windows without `ControlMaster` because neither layer requires it: Remote-SSH can keep an ordinary `ssh.exe` dynamic-forward process alive, while application forwards are local listeners multiplexed as remote-agent tunnel requests. `ControlMaster` only reduces/reuses SSH authentications/connections on clients that support it.

## 1. Connection launch and lifetime

### Verified publicly

- Remote-SSH uses an OpenSSH-compatible client; VS Code searches `PATH`, then known Git-for-Windows locations, and `remote.SSH.path` can select the executable ([official client setup](https://code.visualstudio.com/docs/remote/troubleshooting#_installing-a-supported-ssh-client)). PuTTY is not supported ([Remote-SSH limitations](https://code.visualstudio.com/docs/remote/ssh#_remote-ssh-limitations)).
- A public Remote-SSH diagnostic log records `useLocalServer`, `useExecServer`, and `enableDynamicForwarding`, then a local supervisor spawning an SSH child with `-T -D`, recording its PID, and terminating the local server on failure ([Microsoft issue #10939](https://github.com/microsoft/vscode-remote-release/issues/10939)). Thus the “local server” is a local helper/supervisor around the SSH/install/bootstrap flow; it is not the remote VS Code Server.
- OpenSSH `-D [bind_address:]port` installs a local SOCKS4/5 listener and forwards its connections over SSH; `-T` disables pseudo-terminal allocation ([`ssh(1)`](https://man.openbsd.org/ssh#D), [`-T`](https://man.openbsd.org/ssh#T)). Remote-SSH requires TCP forwarding on the SSH server for its control tunnel ([official troubleshooting](https://code.visualstudio.com/docs/remote/troubleshooting#_enable-tcp-forwarding-on-the-remote-host)).
- VS Code’s remote server normally listens on a random remote loopback TCP port, authenticated with a random key, although Linux/macOS hosts may use a Unix socket instead ([official security description](https://code.visualstudio.com/docs/remote/troubleshooting#_improving-security-on-multi-user-servers)). All client/server communication is through the authenticated SSH tunnel ([official FAQ](https://code.visualstudio.com/docs/remote/ssh#_what-are-the-connectivity-requirements-for-the-vs-code-server-when-it-is-running-on-a-remote-machine-vm)).
- Official troubleshooting says the traditional flow makes two SSH connections: one to install/start/find the server and one to create the SSH tunnel used to reach it ([documentation](https://code.visualstudio.com/docs/remote/troubleshooting#_connecting-to-systems-that-dynamically-assign-machines-per-connection)). Closing the remote connection or exiting VS Code closes the session ([official disconnect behavior](https://code.visualstudio.com/docs/remote/ssh#_disconnect-from-a-remote-host)).
- `ControlMaster` is **not a Remote-SSH prerequisite**. VS Code documents it as an optional way to multiplex sessions and reduce repeated authentication, explicitly for macOS/Linux clients ([authentication documentation](https://code.visualstudio.com/docs/remote/troubleshooting#_enabling-alternate-ssh-authentication-methods)); Microsoft’s issue tracker likewise records that native Windows OpenSSH does not provide this option ([issue #3938](https://github.com/microsoft/vscode-remote-release/issues/3938)). OpenSSH defines `ControlMaster`/`ControlPersist` as connection-sharing controls ([`ssh_config(5)`](https://man.openbsd.org/ssh_config#ControlMaster)).
- `-L` is still supported independently through SSH configuration. VS Code documents `LocalForward` as the way to create an **always-on/static** forward ([official Remote-SSH guide](https://code.visualstudio.com/docs/remote/ssh#_always-forwarding-a-port)); OpenSSH defines it as a local listener whose traffic is sent over the secure channel to a remote host/port ([`ssh_config(5)`](https://man.openbsd.org/ssh_config#LocalForward)).

### Inference and unavailable detail

- **Inference:** the SSH child stays alive because the local helper owns/supervises it and because the dynamic forward must remain available for the remote-agent session; the issue log demonstrates this ownership but the exact restart/keepalive state machine is unavailable.
- **Unavailable:** `ms-vscode-remote.remote-ssh` implementation source is not in the public `microsoft/vscode` repository. Consequently the exact current differences among `useLocalServer`, `useExecServer`, legacy server mode, process-tree/job-object handling on Windows, reconnect policy, command-line construction, and whether every released configuration uses one versus two OS-level `ssh` processes cannot be verified from source. Public issue logs are observations of particular versions/configurations, not a stable API contract.

## 2. From a requested remote port to a local listener

### Public core path

1. A manual/API/automatic request enters `TunnelModel.forward`. Unless a local port was supplied, the requested local port defaults to the remote port ([model forwarding path](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/services/remote/common/tunnelModel.ts#L701-L755)).
2. `TunnelService.openTunnel` either calls a registered resolver-provided tunnel provider or the built-in tunnel implementation ([selection logic](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/common/tunnel.ts#L347-L402), [built-in/provider branch](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L182-L221)).
3. Built-in `NodeRemoteTunnel` creates one local `net.Server`. It first tries the requested/same-number port, searches nearby, and finally lets the OS choose port `0` if necessary ([local selection/listen](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L87-L111)). The default bind is `127.0.0.1`; `remote.localPortHost` can choose all interfaces ([bind policy](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/common/tunnel.ts#L249-L252)).
4. On each local connection, it calls `connectRemoteAgentTunnel`, obtains a remote socket, and mirrors bytes both ways ([data path](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L113-L170), [remote-agent request](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/remote/common/remoteAgentConnection.ts#L460-L464)). Disposal closes the local server and all paired sockets ([cleanup](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L73-L85)).

Therefore a Ports-view temporary forward is, in the public default path, **a VS Code local TCP proxy over the existing remote-agent connection**, not raw `ssh -L` and not a new SSH process per port. Static `LocalForward` entries are a separate, raw-OpenSSH mechanism. A resolver can supply a different tunnel factory, so claiming that every Remote-SSH release/configuration always follows the built-in path would exceed the public evidence ([tunnel-provider API](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/tunnelFactory.ts#L22-L91)).

Conflict behavior is best-effort same-port rather than strict same-port: official docs say remote 3000 may become local 4123 when occupied ([user documentation](https://code.visualstudio.com/docs/remote/ssh#_temporarily-forwarding-a-port)). `requireLocalPort` only requests a modal warning when the selected port differs; it does not turn selection into an atomic hard failure ([setting definition](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L273-L277), [mismatch dialog](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/services/remote/common/tunnelModel.ts#L680-L696)).

## 3. Automatic discovery, policy, actions, and cleanup

### Process/socket discovery (`process`, Linux remotes only)

The remote Node extension host periodically reads `/proc/net/tcp` and `/proc/net/tcp6`, keeps LISTEN (`0A`) sockets, maps socket inodes through `/proc/<pid>/fd`, and reads process `cwd`/`cmdline`; it has a heuristic fallback for sockets owned by root-visible processes ([scanner implementation](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L32-L179), [collection routine](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L248-L322)). Only loopback/all-interface candidates are retained; scans run no faster than every two seconds and slow in proportion to measured scan cost ([scan loop](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L202-L246)).

The first snapshot is treated as pre-existing and is not automatically forwarded unless an explicit matching attribute exists. Later candidates are forwarded; when an auto-forwarded candidate disappears, its tunnel is closed and its session properties cached for reuse ([process forwarder](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L647-L843)). The scanner excludes VS Code Server command lines and candidates without attributable process detail from ordinary auto-forwarding ([scanner exclusion](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L99-L145), [candidate checks](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L728-L771)).

### Output discovery (`output`) and `hybrid`

`output` parses local-looking URLs from integrated-terminal and debug output and forwards matches; it necessarily misses services that print no URL ([setting semantics](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L232-L241), [URL-forwarder path](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L569-L640)). Output-only forwards are not automatically removed until reload/manual close. `hybrid` discovers from output but uses process disappearance for unforwarding ([settings reference in source](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L232-L241)). On Windows or macOS **remote hosts** (not client OS), `process`/`hybrid` have no effect and VS Code forces output discovery ([configuration text](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L232-L241), [runtime selection](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L319-L349)).

`remote.autoForwardPorts` defaults true, but disabling it does not prevent extension-requested forwards or every URL-triggered forward ([setting definition](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L227-L241)). If default process discovery creates more than 20 automatic forwards, VS Code changes the workspace to `hybrid` and offers Undo; explicit source configuration suppresses this fallback ([fallback setting](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L243-L246), [switch behavior](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L256-L317)).

### Policy and UX

`remote.portsAttributes` accepts a port, range, host:port, or process-command regex. Per-match attributes include `onAutoForward` (`notify`, `openBrowser`, `openBrowserOnce`, `openPreview`, `silent`, `ignore`), `elevateIfNeeded`, label, `requireLocalPort`, and HTTP/HTTPS protocol; `remote.otherPortsAttributes` supplies defaults ([settings schema](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L253-L344)).

After an auto-forward, VS Code applies those actions, rate-limits ordinary notifications to one per five seconds, supports browser-once per local address, and uses a three-second heuristic to avoid noisy high-numbered/debug ports winning over likely application ports ([action implementation](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L353-L468)). The Ports view reports the actual selected local port; users may rename it or change its local port ([official guide](https://code.visualstudio.com/docs/remote/ssh#_change-local-port-on-tunnel)).

Manual forwards can be persisted per workspace/profile when `remote.restoreForwardedPorts` is true; VS Code stores tunnel metadata with an expiration and restores non-extension tunnels later ([setting](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L222-L226), [restore/storage implementation](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/services/remote/common/tunnelModel.ts#L568-L679)). Closing a tunnel disposes the listener; ending an auto-detected process closes only auto-sourced tunnels, while ending the remote session/disposing the tunnel service closes all listeners and sockets ([auto cleanup](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L799-L843), [service disposal](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/common/tunnel.ts#L292-L305)).

## 4. Why native Windows works without `ControlMaster`

The client OS and remote OS must not be conflated:

- A native Windows **client** can run the supported Win32 OpenSSH `ssh.exe` ([official client matrix](https://code.visualstudio.com/docs/remote/troubleshooting#_installing-a-supported-ssh-client)). Its ordinary `-D` session is sufficient to carry the VS Code transport; `ControlMaster` merely multiplexes multiple SSH sessions at OpenSSH’s connection layer ([OpenSSH options](https://man.openbsd.org/ssh_config#ControlMaster)).
- Once the VS Code remote-agent connection exists, the public application-forward implementation multiplexes each accepted local socket through `connectRemoteAgentTunnel`; it does not ask OpenSSH for a new control operation and does not need a control socket ([local proxy implementation](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L113-L170)).
- Port **discovery runs remotely**. For the project’s Linux Development Host, `/proc` process/socket discovery is available regardless of whether the UI client is Windows, macOS, or Linux ([Linux gate and remote-host setup](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L188-L201)).

Accordingly, Windows support comes from long-lived ordinary SSH plus an application-level multiplexer, not from emulating `ControlMaster`. The cost is that multiple bootstrap SSH connections may authenticate separately and can land on different backend nodes; VS Code documents `ControlMaster` only as the macOS/Linux workaround for that special load-balanced-host case ([official limitation/workaround](https://code.visualstudio.com/docs/remote/troubleshooting#_connecting-to-systems-that-dynamically-assign-machines-per-connection)).

## 5. Recommendations for the standalone bridge

### Adopt

- **Remote discovery on Linux, based on kernel socket state**, not terminal text. Model candidates as `(bind address, port, PID, command)` and restrict the default product scope to loopback/all-interface listeners, as VS Code does ([public scanner](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/api/node/extHostTunnelService.ts#L202-L322)). For a headless Go agent, prefer direct `/proc` traversal over shelling out to `ls | grep`.
- **Separate discovery, policy, desired state, and forwarding backends.** VS Code’s candidate stream, attributes, tunnel model, and tunnel service are distinct seams ([candidate/model boundary](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/services/remote/common/tunnelModel.ts#L880-L944), [service boundary](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/common/tunnel.ts#L347-L402)). This maps well to saved policies plus system-OpenSSH controllers.
- **Track provenance and lifecycle.** Distinguish automatic, user-requested, and static/configured forwards; only automatically remove automatic ones when listeners disappear. Cache chosen local ports to avoid churn ([VS Code lifecycle](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L799-L843)).
- **Make conflict policy explicit.** Like VS Code, this product prefers the remote port locally, but it uses a deterministic bounded `port + 1` fallback and supports a strict `requireSamePort` policy. Always expose the Allocated Local Port and represent exhausted allocation as a first-class conflict state rather than silently choosing an arbitrary port. `ExitOnForwardFailure=yes` remains relevant when comparing against raw `ssh -L` behavior ([`ssh_config(5)`](https://man.openbsd.org/ssh_config#ExitOnForwardFailure)).
- **Default to loopback binding, debounce scans/events, suppress notification storms, and provide per-port ignore/notify/open-browser policy**, borrowing behavior rather than VS Code’s exact settings syntax ([bind default](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/common/tunnel.ts#L249-L252), [notification throttling](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/browser/remoteExplorer.ts#L353-L468)).
- **Design Windows as a backend choice, not a ControlMaster port.** A future Windows controller can own one long-lived `ssh.exe -N` with declared `-L` forwards, restart transactionally when desired forwards change, or implement an application-level multiplexed transport. OpenSSH documents `-N` as “no remote command,” suitable for forwarding-only sessions ([`ssh(1)`](https://man.openbsd.org/ssh#N)).

### Do not copy

- Do not copy terminal/debug-output URL parsing as the primary detector; VS Code itself documents its misses and inability to unforward in output-only mode ([settings semantics](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/workbench/contrib/remote/common/remote.contribution.ts#L232-L241)).
- Do not copy VS Code’s remote-agent tunnel protocol or local Node proxy. It is tightly coupled to VS Code Server, resolver APIs, extension-host RPC, URI openers, and web/public-tunnel concepts ([core proxy dependencies](https://github.com/microsoft/vscode/blob/96f2210282fa5c1528ecac70a73180c4d6292c89/src/vs/platform/tunnel/node/tunnelService.ts#L174-L221)). The standalone product explicitly chooses system OpenSSH and should keep that auditable boundary.
- Do not copy arbitrary local-port substitution when a policy requires the same port, browser-preview/public-privacy concepts, workspace-profile restore semantics, or the “first snapshot is ignored” rule wholesale. They are editor UX choices, not invariants of a host bridge.
- Do not depend on undocumented Remote-SSH internals (`useLocalServer`, `useExecServer`, install-script parsing, askpass wiring, process supervision). They are closed-source implementation details evidenced only by version-specific issue logs ([example log](https://github.com/microsoft/vscode-remote-release/issues/10939)).

## Confidence boundary

High confidence: public VS Code core discovery, tunnel-model, local-listener, conflict, notification, and cleanup behavior; official SSH architecture and ControlMaster guidance. Medium confidence: observed Remote-SSH command lines and helper/process roles, because evidence is official issue logs rather than extension source. Unknown: the exact current Remote-SSH resolver/tunnel-provider branch and OS-specific process supervision, because the extension implementation is closed-source.
